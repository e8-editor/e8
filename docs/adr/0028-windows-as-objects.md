# 0028. Windows as objects

Status: accepted · 2026-10-30 · its decision that windows stay ids in scripts, and its note that internal windows have no ids, superseded by [0069](0069-windows-as-emacs-has-them.md)

## Context

[ADR 0026](0026-the-next-foundations.md)'s last step began with windows: a window was an id, a buffer, a size and a top line, with the selected window's point and top line kept in its buffer and the others' points as markers there. Emacs's windows are objects with more to them, and Lisp that ports leans on it: `save-window-excursion` and `quit-window`'s restore need a frame's windows saved and put back; `display-buffer` records how to undo itself in a `quit-restore` parameter; dedicated windows keep their buffer; `C-x <left>` and `C-x <right>` go through the buffers a window showed; and a window that is not selected keeps the text at its top when lines are added above it, as its start is a marker. Here a window's top was a line number, so typing above it in another window scrolled it, and window.ts kept `quit-restore` in a map of its own.

## Options considered

1. **Window objects as values** (`Value::Window`), as Emacs's are, with their state behind them.
2. **Window ids as now**, with the state Emacs keeps in a window object kept in the core's `Window`, and the functions on it under Emacs's names.

## Decision

Option 2: window ids stay what scripts hold, since they are never reused and compare as Emacs's window objects do; making them values can come with frames as values. What a window holds grows to Emacs's:

- **Start.** A window that is not selected keeps where it starts in its buffer beside its point, a position that moves with edits as Emacs's window-start marker does; the selected window's top line moves with text added or deleted above it too. `window-start`, `set-window-start`, `window-point` and `set-window-point` read and set them for any window; a window still starts at a line's start.
- **Parameters**: `window-parameter`, `set-window-parameter` and `window-parameters`. window.ts keeps `quit-restore` there in Emacs's shape, `(window window SELECTED BUFFER)` for a window made for BUFFER, `(frame frame ...)` for one on a frame made for it, and `(other (PREVIOUS START POINT HEIGHT) SELECTED BUFFER)` for one that showed PREVIOUS, its first element `same` once BUFFER is shown in it again, as display-buffer-record-window writes it.
- **Dedication**: `window-dedicated-p` and `set-window-dedicated-p`, as Emacs's window.c and window.el use them. `set-window-buffer` refuses to show another buffer in a strongly dedicated window and stops a softly dedicated one being so; typed, `C-x b` in a strongly dedicated window is refused, as `switch-to-buffer-in-dedicated-window` is nil in Emacs, while from code `switch-to-buffer` shows the buffer in another window; `previous-buffer` and `next-buffer` refuse; `display-buffer` may split a dedicated window but does not reuse one, and pops up a frame when every window is; killing the buffer of a dedicated window deletes the window, or its frame if it is the frame's only window and there are others.
- **The buffers it showed**: `window-prev-buffers`, with where each started and its point, kept in the buffer so they follow edits as Emacs's markers there do, recorded whenever a window shows another buffer, as record-window-buffer does, which also forgets `window-next-buffers`. `switch-to-prev-buffer` and `switch-to-next-buffer` are window.el's, ported to the core because killing a buffer runs them in each window showing it: back through the window's own buffers, then through the buffer list. `previous-buffer` on `C-x <left>` and `next-buffer` on `C-x <right>` call them, and `switch-to-buffer` shows a buffer where the window last showed it, as `switch-to-buffer-preserve-window-point` says. A window made by splitting or by `display-buffer` starts with none, as in Emacs.
- **The buffer list's order**: buffers are listed most recently selected first, as Emacs's `buffer-list` orders them, by `bufferList()`, buffer-name completion, `save-some-buffers`, and `other-buffer`, which `C-x b` offers and `switch-to-prev-buffer` and `kill-buffer` fall back on, passing over buffers a window shows as Emacs's does. `switch-to-buffer` and `select-window` put a buffer first, and `bury-buffer` last.
- **Where a buffer shows again**: a window stopping showing a buffer notes where it started, as Emacs's unshow_buffer, and leaves its point as the buffer's unless the selected window shows it; the next window to show the buffer starts there, recentred if its point would be out of sight, as redisplay would.
- **Configurations**: `current-window-configuration` saves the selected frame's tree, each window's buffer, start and point (as markers, so they follow edits), size, parameters, dedication and buffer history, which window is selected and which buffer current; `set-window-configuration` puts them back, windows deleted meanwhile coming back under their ids and others going, and a buffer killed meanwhile replaced by another. Scripts hold a configuration as an object the editor frees when nothing refers to it, and `saveWindowExcursion` runs code and puts the windows back however it ends.

## Review

An independent review compared these with Emacs 30.2 and found twelve differences, which the same round fixed. Killing a buffer showed one replacement in every window, chosen for the whole editor, where each window in Emacs goes back to its own previous buffer, where it was; `previous-buffer` and `next-buffer` failed when a window's own list ran out, where Emacs goes on through the buffer list, and moved the buffer left to the end of the previous buffers, where Emacs leaves it first and skips the next buffers; showing another buffer kept the next buffers, which Emacs forgets; killing the buffer of the selected dedicated window kept the window, still dedicated; dedication was not enforced or reset where Emacs does it; `quit-window` did not restore the reused window's point and fell back on `switch-to-buffer` rather than the window's previous buffer; the quit-restore parameter was a shape of E8's own; `set-window-configuration` restored point in the buffer that was current, which Emacs leaves alone, left the wrong buffer current inside the minibuffer, and threw on a deleted frame's configuration, where Emacs returns nil; the selected window's start did not follow edits; and `switch-to-buffer-preserve-window-point` was missing.

`window-prev-buffers` entries now live in the buffer beside window points, so they follow edits; the buffer list has Emacs's order; and the Emacs comparison has the review's key sequences as cases, its recorder starting each case with a window that has shown nothing and the same buffer order whatever earlier cases did. Emacs's own buffers are in E8's runs of the cases too, *Messages* and *scratch* after the case's, as the fallbacks reach them; what *Messages* holds differs, so a case that ends in it compares only which windows show it.

## Consequences

`save-window-excursion`, `quit-window` and the prev-buffer commands work as their Lisp does, and ports of winner, ediff and transient have what they save and restore. Still to come: a window starting partway through a line, which needs the rows to begin mid-line; `switch-to-prev-buffer-skip`, `switch-to-visible-buffer` and frames' `buffer-predicate`; frames' own buffer lists, which Emacs keeps beside the global one; restoring a quit window's height; hiding a frame where Emacs's `quit-window` would; `window-hscroll`, which the front ends work out for themselves; the minibuffer's window in the window tree; window objects as values; and `window-state-get` and `window-state-put`, which write a configuration as data.

## Dependencies introduced

None.
