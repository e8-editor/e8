# 0069. Windows as Emacs has them: window.c's tree, window.el's policy, windows as objects

Status: accepted · 2026-11-11

## Context

[ADR 0009](0009-windows.md) gave E8 windows as a binary tree of splits that the core keeps and front ends lay out, sizes in lines and columns, a resize that moves one split line, and `display-buffer` as window.el's default actions written into `window.ts`. [ADR 0028](0028-windows-as-objects.md) gave a window what Emacs's window object holds, but kept it a number in scripts. [ADR 0017](0017-frames.md) gave frames, one size for all, one minibuffer, and egui viewports. Window and frame accessors followed with the parity work (e8-editor/e8 pull request 96).

E8's goal is to host Emacs's packages, ported from Emacs Lisp to TypeScript as faithfully as the language allows. Measured against that goal, the window design was a shortcut taken on the first day to get `C-x 2`, `C-x 3` and `display-buffer` working, never revisited, rather than a design with reasons of its own:

- **Emacs does windows in two layers.** window.c keeps a tree of live and internal windows, each a Lisp object, with combinations of any number of children, sizes in pixels (a cell on a terminal), normal sizes, a combination limit, and a resize protocol (`window-new-total`, `window-new-normal`, `window-new-pixel`, `window-resize-apply`) that does nothing on its own. window.el, 11,023 lines of Lisp, holds all the policy on top: resizing and preserved sizes, `fit-window-to-buffer`, balancing, side windows and atomic windows, `display-buffer` with `display-buffer-alist` and its action functions, `quit-restore`, and window states. E8 has neither layer's shape: anonymous splits, minimum sizes as constants, and policy of its own, written fresh where window.el's existed.
- **Ports work around it.** e8-popper dropped `popper-window-height` and `popper-display-function`, as there is no `display-buffer-alist` and no side windows. e8-magit writes Magit's display functions out by hand and walks `windowTree()` summing widths to stand in for window edges. e8-vundo and e8-org-roam split the root window to stand in for a side window. transient deletes its window and splits again to resize it. Ediff's panel cannot be smaller than four lines.
- **Packages expect window.el.** Of MELPA's 295 most downloaded packages read for [docs/parity/demand.md](../parity/demand.md), 148 call a function window.el or frame.el defines; `display-buffer-alist` appears in 16, `display-buffer-in-side-window` in 14, `display-buffer-reuse-window` in 14, `fit-window-to-buffer` in 19, `window-resize` in 10. After the accessors, the window tree is still the group of missing primitives most needed, wanted above all by window.el itself.
- **Windows and frames as numbers cost more than they save.** `windowp` and `framep` cannot be answered, and about 17 of Emacs's packages, 16 of MELPA's and 5 of a daily configuration's ask them, mostly to tell what kind of argument came in. Window 1 and frame 1 exist together, so the many Emacs functions taking a window or a frame in one argument (`window-list`, `next-window`'s ALL-FRAMES, `walk-windows`, `get-buffer-window`) are ambiguous. TypeScript cannot tell a window from a frame, a position or a count. And E8 already gives scripts buffers, markers, keymaps and window configurations as small objects holding an id, so windows and frames are the odd ones out.
- **Nothing E8 does better than Emacs depends on the difference.** Front ends laying the frame out in their own units comes from the frame description and `WindowTree::rects`, which any tree can feed; the editor's own thread and front ends drawing from a description ([ADR 0050](0050-the-frame-description.md), [ADR 0051](0051-the-editor-thread.md)) describe whatever tree there is; and the ideas in [departures.md](../departures.md) need display properties and a window's width, not E8's tree. ADR 0009's one stated reason, that front ends measure in different units, argues against the core owning one front end's pixels, not against Emacs's tree; and since [ADR 0029](0029-redisplay-beyond-rows.md) the core has the front end's metrics, as Emacs's window.c has its frame's.

## Options considered

1. **Keep the design; add what packages ask for on top of it.** `display-buffer-alist` and side windows written for E8's tree, `fit-window-to-buffer` its own way. Smallest, but each later window.el feature is written again rather than ported, resizing keeps behaving unlike Emacs's, and none of it can be checked against window.el's code.
2. **Emacs's two layers, windows still numbers.** window.c's tree in Rust and window.el's policy in TypeScript, with windows and frames left as numbers in scripts and sizes in lines and columns.
3. **Emacs's two layers, windows and frames as objects, sizes as Emacs's.** Option 2, with windows and frames as handle objects in scripts, as buffers and markers are, and sizes in the front end's units, a cell on a terminal, as Emacs's window.c keeps them.

## Decision

Option 3: E8's windows follow Emacs's throughout, with no difference kept by design. The work goes in stages, each a series of pull requests that lands on its own behind `make check`, a review, and oracle cases recorded from Emacs (`"windows": true`) for what it ports:

1. **Windows and frames as objects.** `Window` and `Frame` in the prelude, as `Buffer` and `Marker` are: small frozen objects holding an id, one per window or frame, which the editor keeps. Rust keeps working with ids; the prelude converts at the boundary, as it does for buffers. `windowp`, `framep`, `window-live-p`, `frame-live-p` and `window-valid-p` answer as Emacs's do, a deleted window's object stays a window that is not live, and windows print as `#<window 3 on *scratch*>`. Window and frame ids come from separate spaces so the boundary can always tell them apart. Every script function taking or returning a window or frame takes or returns these, accepting a number too until the packages and the ports have moved; `packages/*.ts` move in the same series, and the ports in e8-editor follow, each in its own repository. The agent and e8-mcp give and take ids, as they do buffers' names.
2. **`display-buffer` as window.el has it.** `display-buffer-alist`, `display-buffer-base-action`, `display-buffer-overriding-action`, `display-buffer-fallback-action` and the action functions (`display-buffer-same-window`, `-reuse-window`, `-reuse-mode-window`, `-pop-up-window`, `-use-some-window`, `-use-least-recent-window`, `-below-selected`, `-at-bottom`, `-in-direction`, `-in-previous-window`, `-in-side-window`, `-no-window`, `-pop-up-frame`), with their alist entries (`window-height`, `window-width`, `side`, `slot`, `dedicated`, `inhibit-same-window`, `reusable-frames`, `window-parameters`, `preserve-size`), ported from window.el into `window.ts`. Side windows are window parameters (`window-side`, `window-slot`) and splits at the root, as window.el makes them. This works on today's tree, written in window.el's shape so the next stage changes what it calls, not what it is.
3. **window.c's tree in the core, with Emacs's sizes.** `WindowTree` becomes a tree of combinations of any number of children. An internal window has an id and an object, with the parameters, normal size and combination limit Emacs gives it. Sizes are kept as Emacs keeps them: each window's total and body sizes in the front end's units, the default font's character size and the mode line's, header line's and tab line's heights coming from the front end's metrics, so a cell on a terminal and points in the GUI, with sizes in lines and columns derived from them as window.c derives them. `window-parent`, `window-top-child`, `window-left-child`, `window-next-sibling`, `window-prev-sibling`, `window-normal-size`, `window-combination-limit`, `window-new-total`, `window-new-normal`, `window-new-pixel`, `window-resize-apply`, `window-resize-apply-total`, `split-window-internal`, `delete-window-internal`, the pixel edges and the rest of window.c's primitives come under Emacs's names. `window-min-height`, `window-min-width`, `window-resize-pixelwise` and `frame-resize-pixelwise` become variables the core reads. Front ends still get a rectangle for each live window, in their own units, as `rects` gives them now. E8's own `resize` and `balance` keep working until the next stage replaces them.
4. **window.el's policy on the tree.** `window-resize` and the rest of window.el's resizing, `window-preserve-size`, `enlarge-window`, `shrink-window`, `balance-windows`, `fit-window-to-buffer`, `shrink-window-if-larger-than-buffer`, `split-window` with its sizes and `split-window-sensibly`, `delete-window` with atomic and side windows, `window-toggle-side-windows`, `window-swap-states`, `window-state-get` and `window-state-put` in Emacs's shape, and `quit-restore-window` with its sizes, ported from window.el into `window.ts`, replacing E8's own; then windmove and winner, which build on it.

Frames' own minibuffer windows, where E8 has one minibuffer for all frames, are frames' part of following Emacs and come under an ADR of their own once this one's stages have landed.

## Consequences

- Ports use window.el's API as packages wrote it: popper's display function and height, Magit's display functions and window edges, vundo's and org-roam's side windows, transient's resize, a one-line Ediff panel. The differences their READMEs list for windows can go, and `windowp` and `framep` port as written.
- window.el's behaviour becomes checkable: each ported function comes with oracle cases, and a difference from Emacs is a bug rather than a design.
- Every package and port that holds a window or frame changes in stage 1; accepting numbers meanwhile lets that happen a repository at a time. The ports' tests, run against `main` by CI's Ports job, show which still pass numbers once the numbers stop being accepted.
- `window.ts` grows by several thousand lines, following window.el's. The core's window module is rewritten around combinations and sizes in the front end's units, which touches splitting, deleting, window configurations, tab-bar's saved configurations, `windowTree()`'s shape, the frame description and the GUI's drag-to-resize. Stage 3 is the risky one: the existing tests and the oracle's window cases must keep passing, and new oracle cases come before old code goes.
- The front ends report the heights of the lines they draw themselves, the mode line, header line and tab line, as part of their metrics, so the core's sizes match what they draw.
- `windowTree()`'s nested `[sideBySide, firstSize, first, second]` shape gives way to the window objects themselves; packages that read it (e8-magit's fullcolumn) use `window-left-child` and its kin, as Magit itself does.
- Watch for: window.el's code depending on frames each having their own minibuffer window, where E8 has one until the frames ADR; and the cost of sizes in the front end's units on the terminal, where they are cells and should cost nothing.
- Superseded by this one once stage 3 lands: ADR 0009's decisions on the tree, its sizes, resizing and display-buffer; ADR 0028's decision that windows stay ids in scripts, and its note that internal windows have no ids. Their other decisions stand.

## Carried out

All four stages landed on 2026-11-11 and 12, each pull request after `make check`, a review against Emacs's source, and the ported packages' tests:

1. Windows and frames as objects: e8-editor/e8 pull request 99.
2. display-buffer as window.el has it: 100.
3. window.c's tree and internal windows (101), sizes in the front end's units (102), and the resize protocol (103).
4. window.el's resizing (104), balancing and fitting (105), splitting and deleting with atomic and side windows (106), window states and quit-restore (108), and windmove and winner (107).

What is left, and where E8 still differs, is in [differences.md](../differences.md)'s window entries: frames' own minibuffer windows (an ADR of their own, as above), splitting on a frame other than the selected one, killing a buffer deleting its windows through the core's older path, and printing window states in a form Emacs reads back.
