# Where things are

What each crate and file holds. [CLAUDE.md](../CLAUDE.md) has the rules for changing them.

- `crates/e8-core`: all editor state and commands. No UI or script dependencies. `buffer.rs` holds a buffer's text, point, mark, markers and overlays, and `buffer/undo.rs` its undo history: recording edits, boundaries, undoing and redoing, in the region too, change groups and `buffer-undo-list`, a module of its own beside the fields it keeps. `properties.rs` holds text properties and overlays, `indirect.rs` makes indirect buffers, each keeping a copy of the text that the editor keeps the same after every change, with one undo history moving to whichever buffer records a change, `textprop.rs` searches them as textprop. `lread.rs` reads and prints Lisp data, as lread.c and print.c, for file-local variables' values (`e8.readFromString`, `e8.prin1ToString`).c does and finds fields (`field-beginning`, `constrain-to-field`, which C-a and the word commands obey), `faces.rs` faces, with Emacs's attributes and anonymous faces, and the colour palette both front ends use, the colour names Emacs knows in `colors_data.rs`, generated by `tests/emacs/colors.el`, `rows.rs` turns a window into display rows: styled segments with hidden text left out, overlay strings and `display` strings shown as Emacs shows them, and what each row shows in its margins and fringes, `image.rs` is image.c: image specs as list values, checked as `valid_image_p` does, and the image cache, which reads an image's size from its header (the `image` crate for PNG, JPEG and GIF, `resvg` for SVG) and works out the size it shows at from `:scale`, `:width`, `:max-width` and the rest; a display spec's image is a segment with an `ImageGlyph`, off the grid, whose row is as tall as its ascent and descent say, shown only when the front end's `TextMetrics::images` says, the text otherwise; pixels are decoded only when a front end draws them (`Editor::image_rgba`), `bidi.rs` is the bidi algorithm as Emacs's bidi.c resolves it, on Emacs's tables in `bidi_data.rs`, generated by `tests/emacs/bidi-data.el`, and `bidi_display.rs` reorders a line's row with it before the row is broken into screen rows, a right-to-left row turned around to run left to right and laid out from the window's right edge (`Row::right_to_left`, `Editor::row_offset_in`), with the bidi primitives, buffers that never held right-to-left text (`Buffer::has_rtl`) skipping it, `fringe.rs` the fringe bitmaps (`define-fringe-bitmap`) and which a row shows (`Editor::window_fringes`, as fringe.c's `update_window_fringes`), when the front end's metrics say its frames have fringes, and the overlay arrow, written over its row where they do not, `font.rs` fonts as values (`Value::Font`: specs, entities and open fonts, with their XLFD names), the questions about them answered by the front end's `TextMetrics` (`font_metrics`, `font_families`, `has_glyph`), `syntax.rs` keeps each buffer's tree-sitter parsers and turns the major mode's captures into faces for those rows, `treesitfns.rs` is treesit.c's primitives: parsers and nodes as values (`Value::Treesit`), a node held as its path from the root and out of date once its tree is parsed again, and queries with Emacs's predicates, `regexp.rs` is Emacs's regexp engine, as regex-emacs.c: Emacs's syntax parsed exactly and matched by a backtracking machine over the buffer, with its syntax table for `\w`, `\sC`, `\_<` and `[:space:]`, back-references and `\=`, and `search.rs` searches with it, literal searches with the `regex` crate, `chartab_data.rs` holds Emacs's character tables, generated by `tests/emacs/unicode.el` (general categories, scripts, the standard syntax table, case and categories), which regexps and the standard syntax table read, `completion.rs` holds the completion styles, as minibuffer.el's patterns, `minibuffer.rs` reading from the minibuffer (` *Minibuf-1*`, a buffer in the buffer list, current while a prompt is open) partway through a command (`completing-read`, `read-file-name`), the sorted completions, and the rows the echo area shows (`minibuffer_rows`), with the strings of the overlays icomplete draws in, `syntax_table.rs` holds syntax tables, as Emacs's syntax.c, and the scanners on them (`scan-lists`, `forward-comment`, `parse-partial-sexp`), `symbols.rs` is the symbol table: each name's variable, a hook's functions, its function cell (a function, a command, or an alias) and its property list, and the advice on its function, `advice-add`'s, which every call by name goes through, `keymap.rs` holds keymaps, which are values (`Value::Keymap`): prefix maps are shared, a keymap's name such as `ctl-x-4-map` is a variable holding it, and a child's prefix maps merge with its parent's, `modeline.rs` formats each window's `mode-line-format` at redisplay, as Emacs's xdisp.c, into segments front ends draw (`Editor::mode_line`), and its `header-line-format` into the header line (`Editor::header_line`), which front ends leave a line for when `Editor::window_wants_header_line` says, `layout.rs` lays rows out as Emacs's redisplay does, with a front end's `TextMetrics` (cells for the terminal and headless editors, egui's fonts for the GUI): each glyph's width and each row's height, rows of the default font's size in a fixed-width font on the grid as before, and the position functions on them, `window.rs` holds the windows and frames and `window_tree.rs` their tree as window.c keeps it: combinations of any number of windows, internal windows with ids of their own, and each child's total size along its combination, shared in proportion when the frame's size changes ([ADR 0069](adr/0069-windows-as-emacs-has-them.md)), which each front end lays out in its own units before telling the core each window's size, `indent.rs` moves by screen lines and answers how rows are laid out, as indent.c (`vertical-motion`, `compute-motion`) and window.c's `window-line-height`, `scroll.rs` how far each window is scrolled horizontally, which redisplay changes to keep point in sight as xdisp.c's `hscroll_windows` does and each row's description carries for front ends to draw, and in the GUI how far up past the top of its first row (`window-vscroll`, which the GUI's smooth scrolling sets), and runs `window-scroll-functions` at redisplay when a window starts elsewhere ([ADR 0071](adr/0071-scrolling-as-emacs-has-it.md)), `insdel.rs` is insdel.c: every change the editor makes goes through `Editor::insert`, `delete_region` and their kin, which refuse read-only buffers and text unless `inhibit-read-only` says otherwise and run `before-change-functions` and `after-change-functions`; `Buffer`'s raw edits are crate-internal. `coding.rs` holds the coding systems, Emacs's 55 commonest under its names (UTF-8, UTF-16, the ISO 8859 and Windows sets, Shift_JIS, EUC, ISO-2022, GBK, Big5) on `encoding_rs`'s tables, with line ends, detection and raw bytes (U+10FF80 to U+10FFFF, shown as `\351`), `charset.rs` the charsets with Emacs's code points, `codingfns.rs` the primitives scripts call (`encode-coding-string`, `detect-coding-region`, `encode-char`), `fileio.rs` reads and writes visited files, with backups, auto-saving and reverting, `fileops.rs` copies, renames and deletes files (to the trash), makes directories and lists them, `filefns.rs` is the file primitives Lisp calls (`insert-file-contents`, `write-region`, the `file-*-p` predicates), each offered first to a handler in `file-name-handler-alist`, `filelock.rs` makes and checks lock files (`.#name`), `decompress.rs` decompresses gzip and zlib data in a buffer, as decompress.c, with `flate2`, `hashes.rs` hashes text for `secure-hash` and `md5`, and `tls.rs` is TLS on network processes, as gnutls.c, with rustls: a connection's socket keeps its threads, and TLS sits between them under a lock, so a plain connection can become TLS; peers are verified recording GnuTLS's warnings rather than refusing, and `tls_stub.rs` stands in for it on the web ([ADR 0075](adr/0075-compression-and-tls-as-emacs-has-them.md)), `casefiddle.rs` changes case as Emacs's casefiddle.c does, with Unicode's special casings and final sigma, `chartab.rs` holds char-tables, which are values (`Value::CharTable`), and `casetab.rs` and `category.rs` the case and category tables built on them, which each buffer has, the standard ones answered by the generated tables while unchanged, `questions.rs` lets a command ask a question and go on with the answer, `kill_ring.rs` keeps the kill ring (`KillRing`: kills joined as consecutive kill commands make them, the yank pointer), `select.rs` links it to the system clipboard a front end supplies, as Emacs's `select-enable-clipboard` does, `keyboard.rs` is keyboard.c's primitives: reading a key partway through a command (`read-key`, `read-key-sequence`), `this-command-keys`, `recent-keys`, and recursive edits, with what the editor keeps of the keyboard in `Keyboard` (keys typed ahead and put back, the keys of a binding so far, the waits open for input), `process.rs` runs programs alongside the editor, as Emacs's process.c, on a pseudo-terminal by default or on pipes, and network connections and servers over TCP and local sockets, each with its coding systems, filter, sentinel and plist, their output taken in when front ends run timers; a process is `Value::Process` by its id, and once gone from the list keeps a record its object still answers from (`Editor::process_info`; [ADR 0070](adr/0070-processes-as-emacs-has-them.md)), pipe processes for a program's standard error, and programs run to the end with `call_process_with` and `call_process_region`, as callproc.c, `users.rs` who runs the editor and on what, as editfns.c and emacs.c ask it (login and full names, user and group ids, the system's users and groups, `num-processors`), and stops the process for the shell as `suspend-emacs` does on a terminal ([ADR 0073](adr/0073-the-user-and-the-system-as-emacs-has-them.md)), `mouse.rs` the mouse as values, as frame.c and window.c give it: where the pointer is, from a cell the front ends write (`PointerCell`), moving it (`Warp`, which they carry out), `<mouse-movement>` events while `track-mouse` is on, and which window and part of it is at a place (`window-at`, `coordinates-in-window-p`) ([ADR 0074](adr/0074-mouse-events-as-emacs-has-them.md)), `terminal.rs` is terminal.c: the one display the editor draws through, as an object with a name, a kind and parameters a package hangs state off, which every frame is on, `frame.rs` is frame.c's geometry: how big the whole of a frame is and where it sits on the screen, which a front end writes in as it draws and asking a frame to move or resize leaves as a request it carries out, the widths of what is drawn around a frame's text, and where a frame's keys go (`redirect-frame-focus`) ([ADR 0077](adr/0077-frames-and-the-window-tree-as-emacs-has-them.md)), `menu.rs` is menu.c and the menu bar: a menu keymap's `menu-item` bindings turned into the lines of a menu, which `x-popup-menu` lays out itself and puts in the frame description as panels of cells for both front ends to draw over the windows, walking it with the keys `menu-navigation-map` binds, as term.c's menus are walked, dialogs (`x-popup-dialog`, `message-box`) as a menu in the middle of the frame and tooltips (`x-show-tip`) as a panel of their own, and laying each frame's menu bar out at redisplay from the `<menu-bar>` bindings of the keymaps in use, as keyboard.c's `menu_bar_items` gathers them ([ADR 0076](adr/0076-menus-as-emacs-has-them.md)), `sysdep.rs` asks the system about its processes (`list-system-processes`, `process-attributes`: libproc on macOS, `/proc` on Linux) and network interfaces (getifaddrs), as Emacs's sysdep.c, `quit.rs` is `quit-flag`: a flag per editor that any thread sets through a `QuitHandle`, checked at safe points by `Editor::maybe_quit` (the regexp matcher, `scan-lists`, every call from a script) unless `inhibit-quit` is set, `specbind.rs` the binding stack, as Emacs's specpdl, which `letBind`, `withCurrentBuffer`, `saveExcursion` and `saveRestriction` push to, so a script stopped without unwinding has its bindings restored, `timers.rs` runs timers and auto-saves when idle (front ends call `Editor::run_timers` when `next_timer_in` says), and `fontify.rs` is jit-lock: `Editor::redisplay`, which front ends call before drawing, runs `jit-lock-functions` on the lines about to show that are not fontified yet. Tests that look at faces call `redisplay` too. `driver.rs` runs the editor on a thread of its own (`Driver`), as both binaries do: input goes to it in order on one channel (keys, `C-g`, and closures to run with the editor), and once nothing waits it redisplays and publishes each frame's description, which the window draws without waiting. `vfs.rs` is the file system the editor uses, `std::fs` natively and on the web a tree in memory (and natively with the `memory-fs` feature, for tests), with `path_exists` and its kin for `Path`'s methods, and `clock.rs` the time, temporary directory and process id, which std panics for on the web ([ADR 0066](adr/0066-e8-in-a-browser.md)). The same loop runs inside a command while a prompt waits (`Editor::wait_until`), so a prompt returns its answer; where no loop runs, a prompt reads keys typed ahead in the same `press`, then an input source (`Editor::set_input_source`, as the oracle's answers), and fails with `end-of-file` without one. Front ends draw rows, never buffer lines, from `frame_description.rs`: after redisplay `Editor::describe_frame` describes a frame as plain data, each window's rows with their glyphs (`display::row_glyphs`), styles and geometry (a right-to-left row's offset, the row point shows on), its fringes, line numbers, mode line and header line, the echo area or minibuffer, and images' pixels, and front ends draw only from it, never asking the editor while they draw, so the editor can run on a thread of its own; laying windows out and hit-testing the mouse are input, which still go to the editor. `Editor` is driven by `handle_key`, `press("C-x C-f")`, `type_text`, or `call(name, args)` for code and tool calls.
- `crates/e8-script`: the script engine and the `e8` API for scripts. The engine is a cargo feature, V8 by default (`v8engine/`) or QuickJS (`quickjs/`), each module holding what only that engine can do: entering it, holding and calling a script's functions; `values.rs` converts values both ways for both, and reads what `defineCommand` is given, over a small trait each implements. `config.rs` finds the config directory and loads `init.ts` for both front ends, and writes `e8.d.ts` and the shipped packages (in `shipped/`) for `tsc`. `batch.rs` is `e8 --batch`, as `emacs --batch`. `strip.rs` erases TypeScript types and puts a check for quitting at the start of every loop's body (the work is in `strip_js.rs`, which `build.rs` also runs on `packages/` when E8 is built, so startup loads them ready to run), `natives.rs` is the table of native functions: each written once, in the `natives!` tables of `natives/` (`images.rs` holds image.c's primitives, `bidi.rs` bidi.c's, `processes.rs` process.c's, taking a `Process` object or its name, `chartab.rs` the char-tables, ...), as a function of the editor and its arguments in Rust types, from which the macro writes the engine's binding, so another engine is another back end rather than a port; `prelude.js` builds the `e8` global from the public natives and its own functions around the rest, `types.rs` generates `e8.d.ts`, the public natives' declarations from their entries.
- `crates/e8-web`: E8 in a browser, built by its `build.sh` and served by `serve.py` ([ADR 0066](adr/0066-e8-in-a-browser.md)). `lib.rs` starts eframe on the page's canvas and the editor's thread as a Web Worker sharing the wasm memory (`web/worker.js`), restores the files `web/storage.js` kept in the browser's storage and sends it each change, and on a touch screen makes scrolling and clicks from a finger's touches (`Touch`); `web/touchkeys.js` gives a touch screen its row of keys and the field the phone's keyboard types into; `web/index.html` is the page. Not tested by `make check` or CI; its README says what works.
- `website/`: E8's website, with E8 running in it, which `.github/workflows/website.yml` builds and publishes to GitHub Pages: `index.html`, `sw.js` (the cross-origin isolation Pages cannot give, added by a service worker), `assemble.sh`, which puts the page, the web build and `docs/assets` together, and the configuration the website's E8 starts with: `init.ts`, the ports `packages.txt` lists, and `config.sh`, which fetches them as `e8.usePackage` installs them.
- `crates/e8`: the terminal binary, and `e8 --batch`. `ui.rs` draws, `main.rs` reads keys and the mouse, and waits on one channel for the terminal's input, the editor's next frame and requests on the agent socket, which it answers as the GUI does. Both front ends count clicks with the core's `clicks.rs`.
- `crates/e8-agent`: E8's agent, an extension the front ends install through `config::setup_with` ([ADR 0019](adr/0019-agent-buffer.md)). `api.rs` streams the Claude Messages API over HTTP on a thread of its own (key from `ANTHROPIC_API_KEY` or the keychain); `lib.rs` runs the conversation from a timer on the editor's thread, writes it into `*agent*` (`agent-mode`, from its own `agent.ts`, built on Org) and runs tool calls, the MCP server's, in the user's window. While the agent acts, the core's `Editor::check_permission` stops writing files, discarding unsaved work, quitting and running code until the user approves. Tests use a scripted model; `tests/live.rs` talks to the real API when run with `--ignored`.
- `crates/e8-mcp`: E8 as an MCP server ([ADR 0015](adr/0015-mcp-server.md)). `lib.rs` answers MCP messages with tools over the command registry (`list_commands`, `describe_command`, `call_command`, `press_keys`, `read_buffer`, `screen`, ...); `socket.rs` is the local socket both front ends listen on (its path in `e8-mcp-socket`) so `e8-mcp` can drive the editor the user sees, or the binary runs a headless editor of its own; `--socket FILE` connects to one editor or fails. A client of the user's editor acts as an agent (`handle_client_message`): what `check_permission` stops is asked of the user, y once, ! always or n, and its tools act in the user's window, never an agent's conversation (`in_window`, shared with `e8-agent`) ([ADR 0062](adr/0062-agents-through-e8-mcp-ask-first.md)).
- `crates/e8-gui`: the egui binary. `app.rs` runs the editor on a thread of its own (`E8App::threaded`), or on the window's thread for tests (`E8App::new`), sending it keys and closures and drawing what it last described, and scrolls smoothly: whole lines go to the core as `<wheel-up>`/`<wheel-down>` keys (bound to `mwheel-scroll`, so rebindable), and only the leftover fraction of a line is kept in the GUI as a pixel offset. `keys.rs` translates egui key events into keys and `app.rs` turns pointer events into mouse keys after hit-testing the windows, `theme.rs` holds the colour tokens and fonts, with fallbacks for CJK, emoji, Hebrew and Arabic, `metrics.rs` the core's `TextMetrics` from egui's fonts, with the system's families from fontique, and the families faces name, which `theme::load_wanted_families` loads between frames ([ADR 0052](adr/0052-faces-in-installed-fonts.md)), `image.rs` draws images from textures of the pixels the core decodes, kept per image id, `clipboard.rs` the system clipboard (⌘C, ⌘X and ⌘V copy, cut and yank through the kill ring, as on Emacs's Mac port), and `modeline.rs` the GUI's own default `mode-line-format`, set before init.ts runs, whose faces `draw_mode_line` maps to tokens. Drawing code takes colours from `Tokens`, never literals.

A major mode's syntax table is NAME-syntax-table, built on its parent's, with the entries its `syntax` option gives, as text-mode.ts and org.ts set theirs. Packages share code by importing it from another package or through the `e8` API, never by copying: Emacs's primitives are there (`charAfter`, `currentIndentation`, `indentTo`, `indentLineTo`, `skipCharsForward`, `saveExcursion`, `syntaxPpss`), and a function a variable names, as `next-error-function`, is made with `e8.defun` and called with `e8.funcall`. A package changes another's function or command with `e8.adviceAdd`, as Lisp uses `advice-add`, rather than redefining it. Scripts keep positions across edits with markers (`e8.makeMarker`, freed with `e8.deleteMarker`), and take back trial edits with `e8.prepareChangeGroup` and `cancelChangeGroup`, as elec-pair.ts does. Text properties a script puts are undone and modify the buffer, as in Emacs; ones that only style text, outside jit-lock, go inside `e8.withSilentModifications`, as comint.ts and compile.ts do. Scripts start programs with `e8.makeProcess`, which asks the agent's permission, and run one to the end with `e8.callProcess`. A mode sets `indent-line-function`, `comment-start` and its syntax table for TAB, `M-;` and the sexp commands, as treesit-modes.ts does. A mode that styles text adds a function to `jit-lock-functions`, as `outline.ts` and `org.ts` do, and a mode can remap commands with `e8.remapCommand`, as org remaps typing for tables. Modal commands such as isearch use `e8.setOverridingMap`, `e8.setKeymapDefault` and `e8.unreadKeys`, as Emacs's Lisp uses `overriding-terminal-local-map`, `[t]` bindings and `unread-command-events`. Define modes with `e8.defineMajorMode` and `e8.defineMinorMode`, which are in the prelude. The editor primitives they use (kill ring rotation, the last repeatable command, recording and replaying macros) are in e8-core. They load at startup, before init.ts, even with `-q`; the list is `PACKAGES` in `e8-script/src/lib.rs`. Each package is an ES module named after its Emacs feature and imports others by that name, as Lisp files `require` each other (`import { truthy, forwardLine } from "subr"`): `subr.ts` holds what subr.el does, and `org-macs.ts` what Org's files share. A package that fails to load is logged and the rest still load. `packages/e8.d.ts` is generated: after changing commands or the script API, run `UPDATE_TYPES=1 cargo test -p e8-script`, then `tsc -p packages` to type-check the packages.
