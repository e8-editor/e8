# E8

A Rust editor that works the way Emacs works. E8 is named in [ADR 0063](docs/adr/0063-the-name-e8.md), after Ember, the placeholder that proved to be Ember.js's, and Gnista ([ADR 0058](docs/adr/0058-the-name-gnista.md)). The original vision is in [docs/brief.md](docs/brief.md), but [ADR 0002](docs/adr/0002-start-simple.md) overrides it: start simple, no sandbox, AI starts as tool calls to commands, and org mode is a package rather than part of the core. Extensions are TypeScript ([ADR 0003](docs/adr/0003-typescript-on-quickjs.md)), run on V8, with QuickJS as the other engine ([ADR 0054](docs/adr/0054-v8-as-the-script-engine.md)); the graphical front end is egui with ArtCraft's look ([ADR 0004](docs/adr/0004-egui-front-end.md)). Every decision since is an ADR, one per area, listed in [docs/adr/README.md](docs/adr/README.md): read the ones for the area you change. E8 is GPL-3.0-or-later ([ADR 0014](docs/adr/0014-gpl.md)); [docs/licensing.md](docs/licensing.md) records which code is derived from Emacs and the alternatives.

The plan for growing E8 towards Emacs parity is in [docs/plan.md](docs/plan.md), and for threads and the script engine in [docs/multithreading.md](docs/multithreading.md). How the work is done, a session per feature on a branch of its own, and what building E8 has taught us, is in [docs/working.md](docs/working.md).

## Current state

A working editor, in a terminal (`e8`) or a window (`e8-gui`), with most of what Emacs is used for every day: files, Dired, projects, windows and frames, search and replace with Emacs's regexps, completion, Org mode with its agenda and capture, a shell, compiling and grepping, tree-sitter modes, faces, images and bidirectional text, an agent that calls commands as tools, and TypeScript extensions (`init.ts`, `M-x load-file`, `M-:`). [docs/features.md](docs/features.md) lists it all, with the keys; [docs/differences.md](docs/differences.md) says where it differs from Emacs.

## Layout

[docs/layout.md](docs/layout.md) says what each crate and file holds; read its part for the code you change.

- `crates/e8-core`: all editor state and commands, and the primitives Emacs writes in C. No UI or script dependencies. Every change the editor makes goes through `insdel.rs` (`Editor::insert`, `delete_region` and their kin), which refuse read-only text and run the change hooks; `Buffer`'s raw edits are crate-internal. Front ends draw rows, never buffer lines, from the frame description (`Editor::describe_frame`, after `Editor::redisplay`), never asking the editor while they draw; `driver.rs` runs the editor on a thread of its own. Tests that look at faces call `redisplay` too. `Editor` is driven by `handle_key`, `press("C-x C-f")`, `type_text`, or `call(name, args)` for code and tool calls.
- `crates/e8-script`: the script engine and the `e8` API. The engine is a cargo feature, `v8` (the default, `src/v8engine/`) or `quickjs` (`src/quickjs/`), which every crate above passes on; lib.rs holds what is the same on both. Native functions are written once, in the `natives!` tables of `src/natives/` (`natives.rs` says how); `prelude.js` builds the `e8` global from them, `types.rs` generates `e8.d.ts`, `strip.rs` erases TypeScript types and puts a quit check in every loop, `config.rs` loads `init.ts`.
- `crates/e8`: the terminal binary. `crates/e8-gui`: the egui binary; drawing code takes colours from `Tokens`, never literals.
- `crates/e8-web`: E8 in a browser, on QuickJS with the editor on a Web Worker ([ADR 0066](docs/adr/0066-e8-in-a-browser.md)); `crates/e8-web/build.sh` builds it, with nightly Rust and LLVM's clang. Code in `e8-core` and `e8-script` reaches files through `vfs` (`use crate::vfs as fs`, and `vfs::path_exists` and its kin rather than `Path::exists`), and the time through `clock`, never std's directly, so the web build sees them.
- `crates/e8-agent`: the agent ([ADR 0019](docs/adr/0019-agent-buffer.md)); while it acts, `Editor::check_permission` stops writing files, discarding unsaved work, quitting and running code until the user approves. `crates/e8-mcp`: E8 as an MCP server ([ADR 0015](docs/adr/0015-mcp-server.md)).
- `packages/`: TypeScript packages that ship with E8, as Emacs ships its preloaded Lisp, each following the Emacs Lisp file of the same name (`simple.ts`, `files.ts`, `org.ts`, ...).
- `examples/init.ts`: a sample config; `examples/packages/example-theme.ts`: a theme to write from, which the theme tests load (type-check with `tsc -p examples/packages`). Ports of packages Emacs does not ship are repositories of their own in `e8-editor`, `e8-vertico`, `e8-consult`, `e8-magit` and the rest ([ADR 0059](docs/adr/0059-packages-are-git-repositories.md)), each with its tests as ERT; [docs/features.md](docs/features.md) lists them, and the `Ports` job in `.github/workflows/test.yml` runs their tests against `main`.

### Writing packages

- Each package is an ES module named after its Emacs feature and imports others by that name, as Lisp files `require` each other (`import { truthy, forwardLine } from "subr"`): `subr.ts` holds what subr.el does, and `org-macs.ts` what Org's files share. They load at startup, before init.ts, even with `-q`; the list is `PACKAGES` in `e8-script/src/lib.rs`. A package that loading turns on, as Emacs's `org-tempo`, goes in `LIBRARY` instead and loads when a config calls `e8.require`, which also finds the user's own packages along `load-path`. A package that fails to load is logged and the rest still load.
- Packages share code by importing it from another package or through the `e8` API, never by copying: Emacs's primitives are there (`charAfter`, `currentIndentation`, `indentTo`, `indentLineTo`, `skipCharsForward`, `saveExcursion`, `syntaxPpss`), and a function a variable names, as `next-error-function`, is made with `e8.defun` and called with `e8.funcall`. A package changes another's function or command with `e8.adviceAdd`, as Lisp uses `advice-add`, rather than redefining it.
- Define modes with `e8.defineMajorMode` and `e8.defineMinorMode`. A major mode's syntax table is NAME-syntax-table, built on its parent's, with the entries its `syntax` option gives, as text-mode.ts and org.ts set theirs. A mode sets `indent-line-function`, `comment-start` and its syntax table for TAB, `M-;` and the sexp commands, as treesit-modes.ts does. A mode that styles text adds a function to `jit-lock-functions`, as `outline.ts` and `org.ts` do, and a mode can remap commands with `e8.remapCommand`, as org remaps typing for tables.
- Scripts keep positions across edits with markers (`e8.makeMarker`, freed with `e8.deleteMarker`), and take back trial edits with `e8.prepareChangeGroup` and `cancelChangeGroup`, as elec-pair.ts does. Text properties a script puts are undone and modify the buffer, as in Emacs; ones that only style text, outside jit-lock, go inside `e8.withSilentModifications`, as comint.ts and compile.ts do.
- Scripts start programs with `e8.makeProcess`, which asks the agent's permission, and run one to the end with `e8.callProcess`. Modal commands such as isearch use `e8.setOverridingMap`, `e8.setKeymapDefault` and `e8.unreadKeys`, as Emacs's Lisp uses `overriding-terminal-local-map`, `[t]` bindings and `unread-command-events`.
- Code that runs on every key or over a whole buffer avoids what is slow in QuickJS, which still runs it ([docs/working.md](docs/working.md)): `Object.freeze` per object, copying large arrays, `matchAll` (use `allMatches` from `subr`), and scanning a whole list where a binary search would do. Nothing may depend on one engine's ways, such as the order a sort calls its predicate or when objects are freed.
- `packages/e8.d.ts` is generated: after changing commands or the script API, run `UPDATE_TYPES=1 cargo test -p e8-script`, then `tsc -p packages` to type-check the packages.

Variables, hooks, named keymaps and the minor mode registry are in `e8-core` (`variables.rs`, `modes.rs`); a Rust command reads a variable with `ed.variable(name)`. A value can be a function (`Value::Function`), as a lambda in Lisp, and `Editor::defun`/`funcall` are the symbols' function cells: a variable such as `indent-line-function` holds a function or a name, and `ed.funcall` calls either. Commands are defined once with named, typed parameters (`Command::new(...).param(...)`); a parameter's prompt, starting input and collection to complete against can be worked out from the arguments read before it, as Emacs's interactive specs are code. Code in the middle of a command can also prompt, with `e8.completingRead`, `readFileName`, `readString`, `yOrNP` and the rest, read keys with `e8.readKey` and `readKeySequence`, or edit recursively with `e8.recursiveEdit`: each returns its answer, as Emacs's does, the command loop running meanwhile, so a hook or a predicate can ask, the command keeps its buffer and prefix argument, and `C-g` unwinds it with `quit` ([ADR 0053](docs/adr/0053-prompts-that-return-their-answer.md)). Awaiting the answer works too, as project.ts does. Rust commands ask with `ed.yes_or_no_p(...)?` and the like. A test that answers a prompt in a later step than the keys that open it drives the editor on a `Driver`, as `crates/e8-script/tests/driven/mod.rs` does; keys given in one `press` answer a prompt they open, and an input source (`Editor::set_input_source`) can answer, as the oracle's does. A command reads its prefix argument with `ed.prefix_numeric()` (a count, 1 by default) or `ed.current_prefix_arg()` (the raw form, to tell plain C-u from a number), as Emacs's interactive "p" and "P" do. A script command declares it instead, as a parameter of kind `count` or `prefix`, and point and the region as `point`, `region-beginning` and `region-end`: the editor fills these without asking, and code passes numbers, `e8.call("forward-paragraph", 2)`, or leaves a count out. Movement commands are marked `.shift_select()`, like Emacs's `^` interactive spec: a shifted key with no binding of its own runs the unshifted key's command and selects as it moves. Interactive use prompts for each parameter in the minibuffer; `Editor::call` takes them directly. Keep it that way: it is what lets scripts, and later the agent, call commands as tools.

Adding a function to the script API is one entry in a `natives!` table in `e8-script/src/natives/`: its parameters and result in Rust types and its documentation, marked `pub` to be `e8.NAME` itself, declared in `e8.d.ts` from the entry (with `#[ts = "..."]` where the TypeScript says more than the Rust types). Only a function that needs JavaScript around its native, for defaults, the prelude's own objects or a callback, also takes a wrapper in `prelude.js` and a declaration in `types.rs`. Prefer making new behaviour a command, which needs none of these. Name it after the Emacs function it stands for, kebab-case as camelCase and `-p` as `P` (`buffer-live-p` is `bufferLiveP`, `skip-chars-forward` is `skipCharsForward`), returning `undefined` where Emacs returns nil; a few older names differ (`fileExists`, `isHook`, `isLocalVariable`). `the_api_defined_is_the_api_declared` in `tests/all/scripts.rs` fails if what `e8` holds and what `e8.d.ts` declares disagree.

## Running

```bash
cargo run -p e8 -- some-file.txt
cargo run -p e8-gui -- some-file.txt
cargo nextest run
cargo clippy --all-targets
make check
make app
```

- `make app` builds `target/E8.app`, the GUI optimised as a macOS app, from the `Info.plist` in `crates/e8-gui/macos/` with the workspace's version, signed for this machine; `make app ENGINE=quickjs` builds it on QuickJS, 41 MB against V8's 97. Opened from Finder it asks the login shell for its PATH, as exec-path-from-shell does for Emacs.app, but has no other shell variables, so the agent reads its key from the keychain. The first launch after each build waits while macOS checks the new program.

- Tests run with cargo-nextest (`cargo install cargo-nextest --locked`): each test in a process of its own, tests from every binary at once, and a test still running after three minutes is stopped and fails (`.config/nextest.toml`). The GUI's snapshot tests are left out of its default set and run with `cargo test -p e8-gui --test window --test images`, as each process spends a minute getting the GPU from Metal. `cargo test` works for everything, a binary at a time. Dependencies are optimised in debug builds (`Cargo.toml`), so the tests that run egui, the script engine and tree-sitter run near release speed. `make check` runs every test and clippy on V8 and then on QuickJS, which the tests must pass on too, building QuickJS in `target/quickjs` so switching engines does not rebuild the workspace; run it before pushing a change to the engines, the natives or the packages. On macOS, Developer Tools must be on for the app that runs the builds (System Settings, Privacy & Security, Developer Tools): Claude.app for a session's builds, Terminal.app for your own. macOS's check of a new program also looks through the folder it is in, and cargo never deletes old debug builds' object files from `target/debug/deps`: at a million files every new test program waited 45 s. `make tidy` deletes those not touched for two days, with the old test programs and incremental caches that take the space, and `make check` runs it first; when tests are slow to start, count that folder's files ([docs/performance.md](docs/performance.md)).

- E8 loads `init.ts` from `$E8_CONFIG_DIR`, else `$XDG_CONFIG_HOME/e8`, else `~/.config/e8`. `-q` skips it. At startup E8 writes `e8.d.ts` there, and `tsconfig.json` if missing, so `tsc -p ~/.config/e8` type-checks the config.
- `cargo run -p e8 -- --print-types` prints the generated declarations.
- A release is a tag `vX.Y.Z` matching the workspace version: bump `version` in `Cargo.toml` in a pull request and merge it. The bump also changes each crate's version of the others in `crates/*/Cargo.toml`, `Cargo.lock` (`cargo update -w`) and the version at the top of `packages/e8.d.ts` (`UPDATE_TYPES=1 cargo test -p e8-script`). `.github/workflows/release.yml` builds `e8` and `e8-mcp` for Apple silicon and Linux, and `E8.app`, after each merge to `main`, and when the version has no tag yet it waits for that commit's tests, tags it and makes the GitHub Release ([ADR 0060](docs/adr/0060-releases.md)). Pull requests are not built. `e8-editor/homebrew-tap` and `e8-editor/nix` pick the release up within a day (`brew install e8-editor/tap/e8`, or the flake), or at once by running their Update workflows (`gh workflow run Update -R e8-editor/homebrew-tap`, and the same for `e8-editor/nix`). If the release fails making the GitHub Release, as it once did with an HTTP 500 from GitHub, `gh run rerun --failed` finishes it. The website (`.github/workflows/website.yml`) is built again after a merge to `main` that changes `website/` or `crates/e8-web/`, which every version bump does; a package's new tag, as e8-themes's, needs `gh workflow run website.yml --ref main`, as the site takes each package at its newest tag.
- `e8 --batch -L . -l test/foo-tests.ts -f ert-run-tests-batch-and-exit` runs a package's ERT tests without a terminal, as `emacs --batch` does, exiting 1 if any failed; `e8 --print-types DIR` writes `e8.d.ts` and the shipped packages into DIR for a package's `tsc`. Packages from git repositories are installed with `e8.usePackage` into `repos/` beside `init.ts`, pinned by `e8-lock.json` ([ADR 0059](docs/adr/0059-packages-are-git-repositories.md)).
- `npm install -g @agentclientprotocol/claude-agent-acp`, then `M-x agent-shell` (or `agent-shell-anthropic-start-claude-code`), talks to Claude Code over ACP, on `claude`'s own login ([ADR 0061](docs/adr/0061-agents-over-acp.md)); `agent-shell-agents` lists the agents it can start. `cargo nextest run -p e8-script --run-ignored ignored-only agent_shell::live` tries the real adapter.
- `claude mcp add e8 -- target/release/e8-mcp` (after `cargo build --release -p e8-mcp`) lets Claude Code use E8: the open GUI or terminal if there is one, asking you before it writes files, discards unsaved work, quits or runs code there ([ADR 0062](docs/adr/0062-agents-through-e8-mcp-ask-first.md)), else a headless editor, which asks nothing. `M-x agent-shell` gives its agents the same, through `e8-mcp --socket`.
- The GUI uses Geist Mono and Inter if they are installed, and egui's built-in fonts otherwise. Without Geist Mono Bold, bold text is drawn twice, slightly apart.
- GUI snapshots live in `crates/e8-gui/tests/snapshots/`. After an intended visual change, run `UPDATE_SNAPSHOTS=1 cargo test -p e8-gui`, then look at the new images before committing them.
- `tests/emacs/` compares E8 with real GNU Emacs on recorded cases (see its README). A case can answer the prompts its keys open (`answers`), compare windows (`windows`), seem to visit a file (`visit`), or visit real ones (`files`, `find`, `disk` for a change on disk at `<f33>`), comparing what the directory holds afterwards, directories (`sub/`) included, and set buffer-local variables first (`vars`). A case left in a Dired buffer is compared as each line's mark and file name, as sizes and dates differ between runs. `E8_ORACLE_ONLY=dired` compares, or records, only the case files whose names have it. After adding or changing cases, record them with `emacs -Q --batch -l tests/emacs/record.el`. `known-gaps.txt` lists where E8 does not match yet. `tests/emacs/README.md` also says how to run the org-mode fuzzer, which finds new differences from Emacs on random documents and keys, and the icomplete oracle in `tests/emacs/icomplete/`, which drives an interactive Emacs on a pseudo-terminal because batch Emacs cannot type into the minibuffer, and the bidi oracle in `tests/emacs/bidi/`, which reads an interactive Emacs's screen through tmux, as batch Emacs has no window to reorder text for.
- `crates/e8-script/tests/bench.rs` times a 50,000-line Org file and a 100 MB text file; [docs/performance.md](docs/performance.md) says how to run it and records the results. The aim is to be faster than Emacs everywhere; [docs/optimisation.md](docs/optimisation.md) lists where E8 is slower than it could be and what would help, each with how it was measured.
- On macOS, `.cargo/config.toml` links with `/usr/bin/cc`, because the Nix `cc` on PATH cannot find the SDK (`library not found for -liconv`).

## Branches, worktrees and pull requests

- Each feature or fix is a branch of its own, worked on in a git worktree by a session of its own: the desktop app makes one per session, and `claude --worktree NAME` does in a terminal, under `.claude/worktrees/`, from `origin/main`. Nothing is committed to `main` directly; it changes only when the human merges a pull request. A fix found in passing goes in a pull request of its own.
- A worktree builds in the main checkout's `target`, through the symlink `.claude/hooks/share-target.sh` makes (run it in a new worktree that has no `target`): V8, egui and the other dependencies are built once, each worktree's own crates are kept apart, and builds in different worktrees take turns on cargo's lock. `make app` in a worktree builds `E8.app` in the worktree's own folder, so each branch has an app of its own and `target/E8.app`, the app the human uses every day, stays the main checkout's.
- Before pushing, run `make check`, and the GUI snapshots when drawing or a package a snapshot shows has changed. CI (`.github/workflows/test.yml`) runs the same tests and clippy on `main` after each merge that changes more than the docs, not on pull requests for now, so `make check` is what a pull request is checked with; it runs on Linux for both engines and on macOS for V8, and the ported packages' tests against the pull request's E8; it does not run the GUI snapshots, which need a GPU. Planned for when E8 settles: feature branches merge into a `stage` branch, CI runs in full on the pull request from `stage` to `main`, and `main` takes it about weekly, with a release. Like the Mac the oracle was recorded on, CI has Ispell and GNU's coreutils first on PATH. Open the pull request against `main` with `gh pr create`, its description as `.github/pull_request_template.md` lays out: what and why, how it was checked, what is not done or not verified.
- Keep a branch current by merging `main` into it. Generated files that conflict are made again rather than merged by hand: `packages/e8.d.ts` with `UPDATE_TYPES=1 cargo test -p e8-script`, snapshots by recording them again and looking at them, `Cargo.lock` by cargo. An ADR takes the next number free on `main`; if `main` takes it first, renumber the branch's before it merges.
- Sessions work in parallel, two or three at once, as their builds take turns on one `target`: each in an area of its own files, and one that changes the script API or the command machinery alone, as it touches `e8.d.ts` and every package. CI tests only `main`, after a merge, so two branches that each pass `make check` are first tested together there: when another branch merges, an open branch merges `main` again and runs `make check` before it is merged in turn. The human merges one pull request at a time. If `main` goes red, fixing it comes before the next merge; releases wait for its tests to pass ([ADR 0060](docs/adr/0060-releases.md)).
- Sessions running `make check` at once load the Mac heavily (a load average of 90 to 100 was seen), and then the tests that time themselves fail without anything being wrong, most often on QuickJS: `edits_and_searches_among_many_overlays_are_quick`, `truncated_rows_look_only_at_their_own_overlays`, `insertions_joining_one_run_are_counted_once` and Org's `indenting_a_long_section_keeps_its_parse`, and, seen at a load of 110, `quit::a_script_that_never_checks_is_stopped_and_its_bindings_restored` on V8 and e8-mcp's `the_binary_passes_messages_to_a_running_editor` on QuickJS. Before blaming a change for such a failure, look at `uptime` and at other worktrees' test programs (`ps -Ao pcpu,comm | sort -rn | head`), rerun only the failed tests on their own on the same engine (`CARGO_TARGET_DIR=target/quickjs` and `--no-default-features --features quickjs` for QuickJS), and say in the pull request which failed under load and how they passed. Org's timed tests allow three times as long with `CI` set, as on CI's runners, which shows whether one is only slow. Start a full `make check` when no other session's is running, if you can.

## Conventions

- Match Emacs names, keys and messages unless there is a reason not to. When behaviour should match Emacs, add an oracle case in `tests/emacs/cases/` rather than guessing what Emacs does. Ideas for doing better than Emacs or Org go in [docs/departures.md](docs/departures.md), for when the base editor is stable, not into the code now. Where E8 behaves differently from Emacs today, deliberately or not yet fixed, is listed in [docs/differences.md](docs/differences.md): add a difference there when one is found or made.
- Regexps that are data (in variables, options, or from users) are Emacs regexps, matched with `e8.emacsRegexp`, `lookingAt`, `reSearchForward` and `matchString`; JavaScript regexps are fine inside a package's own code. Errors are signalled with a condition (`e8.signal`, `userError`) and caught by condition (`e8.conditionCase`), not by their message.
- Commands Emacs writes in Lisp are written in TypeScript ([ADR 0005](docs/adr/0005-rust-core-typescript-commands.md)); Rust is for what Emacs does in C.
- Every feature lands with tests. Behaviour a user sees gets a headless test driven by key sequences: in `crates/e8-core/tests/all/` for the core and `crates/e8-script/tests/all/` for scripts (each one test binary, a file a module listed in its `main.rs`, so a change links one program and macOS checks one new program before it runs; e8-script's oracle, fuzzers, bench and regexp, icomplete and bidi oracles are binaries of their own beside it), and a snapshot in `crates/e8-gui/tests/` for anything drawn differently.
- Decisions go in `docs/adr/NNNN-short-title.md` (template in `docs/adr/0000-template.md`), naming any new dependency and its purpose.
- Never commit API keys or real personal org files.

## Ask the human before

- changing the extension language or its runtime;
- adding a network dependency to `e8-core`;
- relaxing a safety default.
